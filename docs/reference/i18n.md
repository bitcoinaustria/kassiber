# Localization (i18n)

Kassiber's **desktop UI** is localized from i18next-format JSON bundles that
the desktop app embeds at build time. English and German ship today; the
system is built so adding a language or a string is a small, mechanical change.

The **CLI and daemon are not localized.** They speak stable machine codes
(`kind`, error `code`, quarantine `reason`, sync `phase`) and the `--machine`
envelope is a deterministic API contract. Human-facing prose is the GUI's job:
the UI maps codes to translated copy. Do not push locale awareness into the
daemon or change `--machine` output per language.

## Where it lives

```
assets/i18n/locales/<lang>/<namespace>.json   # the bundles, at the repository root
crates/kassiber-desktop/src/i18n.rs           # lookup, interpolation, plurals; embeds the bundles
crates/kassiber-desktop/src/i18n/tests.rs     # en/de key parity, embedded namespaces, duplicate keys
crates/kassiber-desktop/src/checks.rs         # referenced-key check and the scene check
```

`src/i18n.rs` implements the subset of i18next the bundles use: namespaces
(`"transactions:table.title"`, default `common`), nested keys, `{{name}}`
interpolation, and `_zero` / `_one` / `_other` plurals picked by a `count`
argument. Its `bundles!` lists name the namespaces it loads. The paths
`locales/<lang>/<ns>.json` below are relative to `assets/i18n/`.

The app's `lang` preference (`UiPrefs` in `src/persist/model.rs`, saved with
the desktop preferences) is the **single source of truth** for the active
language; there is deliberately no OS language detection. First run defaults
to English. Settings → Appearance switches it; `--lang de` overrides it for
one launch.

## Using translations

```rust
use crate::i18n::{t, tc, tr};

t("settings:appearance.theme.title");                 // other namespace: prefix
t("actions.reset");                                    // `common` by default
tr("settings:appearance.scale.value", &[("percent", "90")]); // interpolation
tc("nav:badge.review", 3, &[]);                        // plural by count
```

## Adding a string

1. Pick a namespace (`common`, `nav`, `settings`, …) or add a new one.
2. Add the key to **both** `locales/en/<ns>.json` and `locales/de/<ns>.json`.
   The bundles must stay in lockstep — the key-parity test fails otherwise.
3. Reference it with `t("key")` (or `t("ns:key")` from another namespace).

Use interpolation, not string concatenation, so word order can differ per
language: `tr("nav:openBook.body", &[("book", ..), ("page", ..)])` → `"{{book}} is now active.
Opening {{page}}."` / `"{{book}} ist jetzt aktiv. {{page}} wird geöffnet."`.
For counts use plurals (`key_one` / `key_other`) through `tc`.

**German register: `du` (informal).** When copy addresses the user directly,
use the informal imperative — `"Wähle die Sprache…"`, not `"Wählen Sie…"`.
Impersonal/infinitive phrasing is fine where it reads naturally.

**Stable ids vs. display labels.** When a code maps to a label (nav routes,
enum→label maps), keep a stable `id`/slug for test ids and lookups and a
separate `labelKey` for display — never derive a test id or a lookup from a
translated string.

## Keeping English & German in sync (dev workflow)

English and German stay aligned because the tooling makes divergence a
build/test failure, not a silent gap. Internalize this:

**Golden rule — never touch one language alone.** Whenever you add, rename, or
remove a UI string, edit **both** `locales/en/<ns>.json` and
`locales/de/<ns>.json` in the same change: same key path, same structure, same
interpolation placeholders.

**Guards that catch mistakes before they ship:**

1. **Referenced keys (test time).** `every_referenced_translation_key_exists`
   in `src/checks.rs` reads every string literal in `src/**/*.rs` shaped like a
   key of a loaded namespace and fails unless it exists in the English and the
   German bundle.
2. **Key parity (test time).** `every_language_keeps_the_english_keys` in
   `src/i18n/tests.rs` fails if any namespace's `en` and `de` key sets differ,
   so a key added to one language but not the other cannot merge. Its
   neighbours check that every namespace on disk is embedded and that no
   object declares a key twice.
3. **Scene check.** `src/checks.rs` renders every scene headless in English
   and German and fails on any lookup that fell back to English or to the key
   at run time (`#[ignore]`d in plain test runs; see the
   [desktop README](../../crates/kassiber-desktop/README.md#checks)).
4. **No silent gap at runtime.** A key missing in German falls back to English,
   and a key missing in both renders as the key string (`settings:foo.bar`).
   Every miss is recorded, and `--i18n-report <file>` writes them out on exit.

**The loop** (from `crates/kassiber-desktop/`):

```bash
cargo test --release            # referenced keys, en/de parity, unit tests
packaging/ci/rune-checks.sh --scenes-only --kassiber-bin ../../target/debug/kassiber
```

`./scripts/quality-gate.sh` and CI's "Desktop app" job run the unit tests,
so a typo'd key or a half-translated namespace cannot merge.

**Terminology — use the glossary, don't improvise.** German is Austrian,
informal `du`. Before inventing a term, check [i18n-glossary.md](i18n-glossary.md):
Bitcoin/space jargon stays English (Wallet, Node, Blockchain, UTXO, Swap,
Peg-in/out, on-chain, Sync, Backend, Provider, Setup, **AI** — not "KI"),
ordinary words translate (Transaktion, Gebühr, Adresse, Guthaben), and the
book/books unit is German (Buch/Bücher). When you settle a *new* term, add it to
the glossary in the same change so it stays consistent across the bundles.

**Review both languages.** Flip the UI in Settings → Appearance, or take a
headless snapshot with `--lang de` (see the desktop README's headless
tooling).

Number/date formatting follows the active language through `src/format.rs`
(de → de-AT: grouping and Austrian month names such as `Jän.`); money stays
currency-driven (see below), so the two are intentionally decoupled.

## Adding a language

1. Add a `Lang` variant in `src/i18n.rs` (`code`, native `label`, `ALL`) and a
   `bundles!` list for it; check the plural rule in `plural_key` (English and
   German share one/other).
2. Create `locales/<code>/<ns>.json` for every namespace (copy English, then
   translate). The key-parity test names the missing keys.
3. Teach `src/format.rs` the language's number and date conventions, and the
   preference parser in `src/persist/model.rs` its code.

## Formatting: two locales, on purpose

- **Money** stays *currency-driven* in `src/format.rs` (`loc`): EUR is always
  grouped de-AT style (`€ 1.234,56`) regardless of UI language, because that
  follows the currency convention, not the reader's language.
- **Dates / language-sensitive numbers** follow the *UI language*
  (`count_in`, the de-AT month names).

These are intentionally separate; do not collapse them.

## Status / remaining work

The desktop UI is transcreated into Austrian German (`du` register) across the
main surfaces, organized into per-surface namespaces (the `bundles!` lists in
`src/i18n.rs`). Terminology follows [i18n-glossary.md](i18n-glossary.md).

- **Reporting language** (per product call): report-output strings stay
  English for now. The desktop translates its exit-tax page
  (`overview:exitTax`), the split-payout card (`transactions:splitPayout`), the
  wallets table (`connections:table`), the refresh progress and sync result
  sentences (`chrome:syncProgress`) and update-check errors
  (`chrome:shell.version.error`).
- **Connection catalog:** the categories and sources' copy (titles, descriptions,
  path/format labels, setup notes) lives under `connections:catalog`;
  `src/overview/catalog.rs` stores those keys and keeps brand, product and
  format names literal.

Migrate a whole surface at a time so a screen is never half-translated, and add
keys to `en` + `de` in lockstep (the parity test enforces it). See the i18n
items in `TODO.md` for the remaining backlog.
